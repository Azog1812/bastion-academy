# 0008 — Per-learner HMAC flags, opt-in scoreboard, TOTP MFA

**Status:** accepted (v4, 30 Oct 2026)

## Context
v3 graded quizzes whose answers sit in a public repository: fine for learning, useless
for any score worth comparing. v4 adds capture-the-flag challenges and a scoreboard, so
flags must not be copyable from the repo or from another learner. A scoreboard also
raises the value of an account, and the threat model listed "no MFA" as an accepted risk.

## Decision

### Flags
`flag = "BASTION{" + hex(HMAC-SHA256(FLAG_HMAC_KEY, "bastion:flag:v1:" + challenge + ":" + user)[0..16]) + "}"`

- **Nothing stored.** Flags are recomputed on demand; a database dump reveals none.
  The key is a separate secret (`FLAG_HMAC_KEY`), so a leak of it can only forge
  scores, never tokens, notes or the audit chain.
- **Per learner.** A flag shared on a forum is worthless to anyone else. A submitted
  flag that matches another learner's is answered like any wrong flag (no oracle on
  other accounts) but recorded as `challenge.flag_shared` with the owner's id. Only
  learners who already solved the challenge can have leaked their flag, so the check
  costs one HMAC per solver, not per user.
- **Constant-time comparison**, per-account rate limit, idempotent solves (points
  stored at solve time, a second correct submission scores nothing).
- **Closed set of artifact generators** (`src/challenges/generators.ts`): content picks
  a kind, it never ships code. Artifacts are derived from a second HMAC, so they are
  stable per learner without storage. Challenges open with their module (same
  server-side gating as lessons).
- **Every generator is proven solvable, and only by solving it.** A test per kind
  recovers the flag the way the brief tells the learner to (brute force, log replay,
  packet decoding, an independent re-implementation of the permission and nftables
  rules), on random flags and seeds, and checks the flag never appears verbatim in the
  artifact. Decoys have the flag's exact format, so filtering by shape does not work.
  Generation is pure CPU and bounded: measured at most ~1 ms and ~57 kB (the blind SQL
  injection log) per artifact, behind the authenticated, rate-limited API.

Rejected: random flags stored per user (a DB leak exposes them, and storage for nothing);
one global flag per challenge (copyable, which defeats a scoreboard).

### Scoreboard
Opt-in: a learner appears only after choosing a pseudonym (`PUT /v1/me/profile`). The
response carries the pseudonym and the score only, never an id or an e-mail (privacy by
default, GDPR art. 25). Score = 10 per validated lesson + challenge points; ties go to
whoever got there first. It is the only cross-user read in the API, and it is documented
as such in the code.

### TOTP MFA (RFC 6238)
- Implemented on `node:crypto` (about 60 lines, checked against the RFC test vectors)
  rather than a dependency (invariant 11).
- Seed: 160 bits, sealed with AES-256-GCM under the KEK ring, AAD bound to purpose and
  user; re-sealed by `cli rotate-keys`.
- Enrolment in two steps (setup with password re-authentication, then enable with a
  first valid code), so a mistyped seed cannot lock a user out.
- **Replay protection:** the last accepted time step is stored and moved forward with a
  compare-and-set `UPDATE`; a code is never accepted twice, even within its window, and
  two concurrent requests with the same code cannot both pass.
- **Login:** after the password, an opaque single-use challenge (SHA-256 stored, 5-minute
  life, 5 attempts) is returned instead of tokens. Wrong codes feed the same progressive
  account lockout as wrong passwords, and the failed-login counter is only reset once
  the second factor passes. The browser flow sets the refresh cookie only after step 2.
- **Recovery codes:** 10 × 80 bits, shown once, stored as SHA-256 (no scrypt needed at
  this entropy), single use, each use audited with the number left.
- **Removal** needs both the password and a valid code: neither a hijacked session nor a
  stolen password alone can turn MFA off.

Rejected for now: WebAuthn/passkeys (phishing-resistant, the better long-term option, but
a much larger surface to build without a library; next step on the roadmap); SMS (SIM swap,
and no sending channel in a local install).

## Consequences
- New required secret `FLAG_HMAC_KEY`: existing installs must add it (`cli gen-secrets`
  prints one); the server refuses to start without it (fail closed).
- `POST /v1/auth/login` and `/v1/session/login` now return either tokens or an MFA
  challenge (`oneOf` in the OpenAPI spec). API clients must handle both.
- TOTP is phishable in real time (a proxy relays the code within 30 s). Replay protection
  limits the window to one use; only WebAuthn removes the risk.
- Flags derived from the platform key only work for artifacts generated by the platform.
  v5 lab containers will receive each learner's flag at start-up, from the same function.
